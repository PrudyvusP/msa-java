# Стратегия миграции данных: Booking Service

## 1. Миграция при запуске нового сервиса

При первом запуске booking-service его база данных пуста, тогда как монолит уже содержит исторические данные о бронированиях. Чтобы новый сервис мог отдавать полный список бронирований, необходимо выполнить начальную миграцию данных.

Подход — одноразовый ETL-скрипт, который считывает все записи из таблицы `booking` монолита и переносит их в таблицу `bookings` нового сервиса. Миграция запускается до переключения трафика, пока монолит продолжает обслуживать все запросы. После копирования выполняется сверка: сравнивается количество записей и контрольные выборки.

Важно: скрипт запускается один раз и не влияет на работу монолита. После успешной миграции оба источника данных (монолит и booking-service) содержат одинаковый набор записей.

## 2. Целевое состояние (TO BE)

После завершения миграции монолит полностью теряет ответственность за бронирования. Таблица `booking` в монолитной базе перестаёт использоваться и может быть удалена.

Архитектура выглядит так:

- **Booking Service** — единственный владелец данных о бронированиях. Все операции создания и чтения идут через его собственную базу данных.
- **Booking History Service** — читает события `BookingCreated` из Kafka и сохраняет полную историю для аналитики. Не участвует в критичном пути бронирования.
- **Монолит** — предоставляет gRPC-эндпоинты для валидации пользователей, отелей, промокодов и отзывов, но больше не хранит и не обрабатывает бронирования.
- **API Gateway** — маршрутизирует запросы `/api/bookings/**` напрямую в booking-service, минуя монолит.

### Преимущества

- Независимое масштабирование booking-service без пересборки монолита
- Отдельная база данных — нет конкуренции за ресурсы с другими модулями
- Асинхронная аналитика через Kafka не влияет на время ответа при создании бронирования
- Возможность отката на любом этапе: если booking-service недоступен, трафик можно вернуть в монолит (пока его код ещё не удалён)
